Product Overview OptiGrid is a full-stack simulation and optimization platform for dynamically allocating limited resources to incoming service requests. It models a service area as a weighted graph, calculates shortest routes, evaluates available resources using a configurable allocation score, and compares the optimized strategy with baseline strategies such as FIFO and nearest-resource allocation. Primary engineering goal: make allocation decisions that balance travel distance, resource workload, request priority, and availability rather than optimizing only one factor. 2. Goals and Non-Goals Goals: real-time resource allocation, shortest-path routing, configurable scoring, workload simulation, baseline comparison, measurable performance metrics, and an interview-friendly visual dashboard. Goals: preserve reproducibility by storing simulation configurations, requests, resources, strategies, and benchmark results in MongoDB. Non-goal: production-grade dispatching for emergency services, financial decisions, or safety-critical operations. Non-goal: machine learning. The optimization logic is deterministic and algorithmic. 3. Target Users Operator/Admin: creates scenarios, manages resources, starts simulations, and compares algorithms. Viewer/Interviewer: watches allocation decisions and inspects metrics, routes, and algorithm behavior. Developer: uses API endpoints and stored benchmark runs to debug and extend the engine. 4. Technology Architecture Frontend: React with JSX. Use React Router for pages, Axios/fetch for REST calls, Socket.IO client for live updates, and a charting library only if needed for benchmark visualization. Backend: Node.js with Express. REST APIs handle CRUD, simulation control, metrics, and benchmark operations. Socket.IO broadcasts resource status, request events, allocations, and metric updates. Database: MongoDB with Mongoose. MongoDB stores scenarios, resources, requests, allocation decisions, simulations, and benchmark results. Optimization engine: C++. The initial implementation is a compiled executable invoked by the Node server through child_process. A future architecture can expose the C++ engine as an independent HTTP service. Important deployment rule: for the prototype, keep the Express server and C++ executable in the same deployment environment so the server can execute the binary locally. Build a Linux executable for Linux hosting; do not depend on a Windows .exe in production. 5. C++ Optimization Engine 11.1 Graph Representation Represent the city as an adjacency list: vector<vector<pair<int,int>>> graph. Each node is a location; each edge stores neighbor and weight. A 10Ã—10 grid produces 100 nodes. The design should support weighted roads so traffic or road conditions can be represented later. 11.2 Dijkstra Use a min-priority queue to compute shortest distances from a source node. Complexity is O((V+E) log V) with an adjacency list and binary heap. 11.3 Allocation Score A configurable deterministic score is recommended: score = wD Ã— normalizedDistance + wW Ã— workloadPenalty + wP Ã— priorityCost + wA Ã— availabilityPenalty. Lower score is better. Keep weights in the scenario configuration instead of hardcoding them. Example: a nearby resource at 90% load can lose to a slightly farther resource at 30% load if the workload penalty is sufficiently large. 11.4 Baselines FIFO: assign the next suitable available resource without optimization. Nearest Resource: choose the available resource with the smallest shortest-path distance. OptiGrid: choose the available resource with the lowest configurable multi-factor score. 11.5 Simulation Use a deterministic pseudo-random generator with a stored seed. Generate request arrival times, source nodes, priorities, service durations, and initial resource locations. Run each strategy against the same generated workload so comparisons are fair. 12. Metrics and Benchmarking Allocation latency: measure the time spent making an allocation decision inside the engine/service. Use a monotonic high-resolution timer. Do not include browser rendering time unless explicitly labeled as end-to-end latency. Average waiting time: mean(request assigned time âˆ’ request arrival time) across completed/assigned requests, with the inclusion rule documented. Utilization: total busy resource-time divided by total available resource-time Ã— 100. Define the simulation interval clearly. Throughput: completed requests divided by simulation duration. P95 latency: 95th percentile allocation decision latency, not just average. Fairness/load distribution: compare assignments per resource and workload variance to detect overloading. Efficiency improvement: baseline-to-optimized percentage = (baseline âˆ’ optimized) / baseline Ã— 100 for metrics where lower is better. For utilization, report the absolute percentage-point change as well as relative change. Resume numbers such as 31 ms â†’ 12 ms, 56% â†’ 84%, or 8.2 â†’ 5.1 minutes must be produced by the benchmark and recorded from actual runs. Do not hardcode or fabricate these values. 13. Express Backend Layering Routes should only map HTTP requests to controllers. Controllers validate input and return HTTP responses. Services contain business orchestration. The engine adapter is responsible for invoking the C++ executable or service. Models contain Mongoose schemas. Socket handlers translate service events into real-time events. Recommended modules: scenarioService, resourceService, requestService, simulationService, allocationService, benchmarkService, engineService. Use centralized error handling, request validation, structured logging, and environment variables for MongoDB and CORS configuration. 17. C++ â†” Express Integration Prototype option: Node child_process.spawn/execFile starts the compiled engine. Prefer spawn when using stdin/stdout streams or long-running simulations. Communicate using newline-delimited JSON or another explicit protocol. Example protocol: Express sends {type:'allocate', request:{...}, resources:[...], graph:[...], weights:{...}}; C++ returns {type:'allocationResult', selectedResourceId:3, routeDistance:4, score:5.2, latencyNs:...}. For a more scalable version, run C++ as a long-lived HTTP/gRPC service and let Express call it over a private network. This avoids launching a process for every request. 18. Security and Reliability Validate all request bodies and IDs. Never pass unsanitized user strings into shell commands; use execFile/spawn with argument arrays rather than shell concatenation. Use authentication if deployed beyond a demo. Restrict simulation-control endpoints to authorized users. Apply CORS restrictions, rate limiting, request size limits, and centralized error handling. Treat the C++ engine as untrusted from the Node process perspective: enforce timeouts, capture stderr, handle exit codes, and reject malformed output. Do not allow arbitrary executable paths from API input. 19. Deployment Recommended prototype deployment: containerize the Node/Express application and C++ engine together. Build the C++ binary during the Docker build stage, install Node dependencies, and start Express. Host MongoDB using MongoDB Atlas or another managed MongoDB provider. Alternative: separate containers for Express and the C++ engine, connected through an internal HTTP API. React can be deployed separately as a static frontend. Do not assume a Windows executable will run on Linux hosting. Compile the engine for the target environment. 21. Request RQ-120 arrives at node 50. Resource 1 is 2 edges away but has 90% load; Resource 2 is 4 edges away with 30% load; Resource 3 is 3 edges away with 70% load. Nearest chooses Resource 1.
